# NFR Traceability Matrix

This matrix maps every Non-Functional Requirement to the architectural
mechanism that satisfies it, the module/component where the mechanism
lives, and a concrete verification method a reviewer can execute.

| NFR | Requirement | Architectural Mechanism | Module / Component | Verification Method |
|-----|-------------|------------------------|--------------------|--------------------|
| **1.1** | Response Time — core journeys (product search, cart, checkout) must minimize round-trip latency under load. | Async FastAPI (non-blocking event loop) + SQLAlchemy `selectin` eager loading (single round-trip per relationship level) + `RequestTimingMiddleware` that adds `X-Response-Time-ms` header and logs slow requests. | `oms/core/middleware.py` (`RequestTimingMiddleware`), `oms/repositories/base.py`, `oms/repositories/order.py` (`get_full`), `oms/routers/product.py` | `curl -s -o /dev/null -D - http://localhost:8000/api/v1/products/search?q=laptop` → inspect `X-Response-Time-ms` header; value < 500 ms under normal load. |
| **1.2** | Concurrency & Resource Utilization — system must exploit available server resources with minimal queuing. | Async I/O throughout (async DB driver `aiosqlite`, async session per request via `get_session` dependency). Uvicorn multi-worker deployment (`--workers N`). Connection pool with `pool_pre_ping` to avoid stale connections. | `oms/database.py` (`create_async_engine`, `get_session`), `oms/main.py` (lifespan), `Dockerfile` / `docker-compose.yml` (worker count) | Run `wrk -t4 -c100 -d10s http://localhost:8000/api/v1/products/search?q=laptop`; observe high throughput with low latency percentiles. Check `/health/ready` queue metrics show workers running. |
| **1.3** | Queue Management — sudden spikes must not crash the system. | Bounded `asyncio.Queue` (`QueueManager`) with N worker coroutines. When the queue is full, `QueueFullError` is raised so the HTTP layer can return 503 instead of OOM-crashing. Workers drain concurrently. | `oms/core/queue_manager.py` (`QueueManager`, `QueueFullError`), `oms/main.py` (lifespan `start`/`stop`) | Inspect `/health/ready` → `checks.queue` shows `max_size`, `current_size`, `worker_count`, `running`. Enqueue more than `queue_max_size` tasks → `QueueFullError` logged, HTTP returns 503. |
| **2.1** | Graceful Degradation — under extreme resource contention, degrade non-essential features to keep core checkout available. | `GracefulDegradationMiddleware` monitors CPU/memory via `psutil` (non-blocking `interval=None`). When either exceeds threshold, non-essential endpoints (`/api/v1/products/search`) return 503 while core endpoints (`/orders`, `/payments`, `/invoices`, `/customers`) remain available. | `oms/core/middleware.py` (`GracefulDegradationMiddleware`, `NON_ESSENTIAL_PREFIXES`, `CORE_PREFIXES`) | Stress CPU > 85% (e.g. `stress -c 4`) then `curl http://localhost:8000/api/v1/products/search` → expect 503 with `{"degraded": true}`; simultaneously `curl -X POST http://localhost:8000/api/v1/orders/ ...` → expect 201. |
| **2.2** | Fault Detection and Recovery — detect internal component failures and automatically attempt to recover or reconnect. | Circuit breaker (`CircuitBreaker`) with CLOSED/OPEN/HALF_OPEN states around the payment gateway call. After `cb_failure_threshold` failures the circuit opens; after `cb_recovery_timeout` it enters half-open and probes. Health readiness endpoint reports open breaker count. DB engine uses `pool_pre_ping` to auto-reconnect stale connections. | `oms/core/resilience.py` (`CircuitBreaker`, `CircuitBreakerRegistry`, `with_circuit_breaker`), `oms/services/payment.py` (`create_payment`), `oms/database.py` (`pool_pre_ping`), `oms/core/middleware.py` (`HealthCheckMiddleware` `/health/ready`) | `curl http://localhost:8000/health/ready` → `checks.circuit_breakers.open_count` is 0 under normal conditions. Simulate gateway failures → breaker opens → `/health/ready` reports `open_count: 1` and status `degraded`. After cooldown, breaker auto-recovers to `closed`. |
| **2.3** | State Preservation — on unexpected process crash, restore operational state and resume processing pending orders with minimal data loss. | SQLite WAL mode (`PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`) for crash-safe durable writes. On startup, `RecoveryService.recover()` scans for orders in non-terminal states (PENDING, ACCEPTED, INVOICED, PAID, SHIPPED) and logs/resumes them. | `oms/database.py` (`init_db` WAL pragmas), `oms/core/recovery.py` (`RecoveryService`), `oms/main.py` (lifespan startup calls `recovery.recover()`) | Create an order (PENDING), kill the process (`kill -9`), restart → check logs for `"Recovery: found 1 order(s) in state pending — resuming processing"`. Verify the order persists via `GET /api/v1/orders/{id}`. Inspect `oms.db-wal` file exists. |
