# NFR Traceability Matrix

| NFR ID | NFR Description | Architectural Mechanism | Module/Component | Verification Method |
|--------|-----------------|-------------------------|------------------|---------------------|
| NFR 2.1 | Graceful Degradation: Under extreme resource contention, the system must degrade non-essential features to ensure core checkout functionality remains available. | Load shedding middleware that monitors average request latency and CPU usage. When thresholds are exceeded, non-essential endpoints (e.g., /users, /products) return 503 while core endpoints (e.g., /orders, /payments, /invoices) remain operational. | Middleware (LoadSheddingMiddleware), Core API routers | 1. Simulate high load (e.g., using locust) on non-critical endpoints.<br>2. Verify that critical endpoints (e.g., /orders, /payments, /invoices) still respond with 2xx/3xx while non-critical endpoints return 503.<br>3. Check middleware logs for overload activation. |
| NFR 2.2 | Fault Detection and Recovery: The application must detect internal component failures and automatically attempt to recover or reconnect, minimizing user-facing errors. | Retry mechanisms with exponential backoff for external services (payment gateway, database). Circuit breaker pattern for external dependencies. Health checks and self-healing via restart policies in container orchestration. | Service layer (retry logic), Database connection pool (SQLAlchemy pool_pre_ping), Docker restart policy | 1. Simulate database failure (e.g., stop DB container) and observe automatic reconnection upon recovery.<br>2. Simulate payment gateway failure and verify retry attempts.<br>3. Check application logs for retry attempts and recovery messages. |
| NFR 2.3 | State Preservation: In the event of an unexpected application process crash, the system must be able to restore its operational state and resume processing pending orders upon restart with minimal data loss. | Persistent storage (SQLite/PostgreSQL) with ACID transactions. All state changes are committed to disk before acknowledging requests. On startup, application replays any pending transactions from the database. | Database layer (SQLAlchemy ORM), Transaction management in service layer | 1. Kill the application process while processing an order.<br>2. Restart the application.<br>3. Verify that the order state is recovered and processing can continue from the last committed state.<br>4. Check that no committed data is lost (verify via database queries). |
