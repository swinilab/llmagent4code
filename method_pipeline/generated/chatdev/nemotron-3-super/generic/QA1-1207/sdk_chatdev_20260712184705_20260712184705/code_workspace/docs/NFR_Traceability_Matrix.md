# NFR Traceability Matrix

| NFR ID | Description | Architectural Mechanism | Component / Module | Verification Method |
|--------|-------------|-------------------------|---------------------|---------------------|
| NFR 1.1 | Response Time: core journeys (product search, cart, checkout) must minimize round-trip latency under load. | - Use asynchronous processing for non-critical paths (e.g., payment processing via Celery).<br>- Implement caching for product catalog using Redis.<br>- Use efficient database indexing and connection pooling.<br>- Deploy multiple Uvicorn workers behind a load balancer (e.g., NGINX). | - API layer (FastAPI endpoints)<br>- Product service (cached reads)<br>- Order service (async payment processing)<br>- Database (PostgreSQL with connection pool)<br>- Redis cache | - Load testing with tools like Locust or k6 to measure response times under simulated load.<br>- Monitor API response times via monitoring (e.g., Prometheus/Grafana).<br>- Verify cache hit rates for product endpoints. |
| NFR 1.2 | Concurrency & Resource Utilization: system must exploit available server resources (up to 98GB RAM class) with minimal queuing. | - Horizontal scaling: multiple API workers and Celery workers.<br>- Asynchronous task queue (Celery) to offload long-running tasks (payment processing, invoice generation).<br>- Database connection pooling (SQLAlchemy pool).<br>- Efficient use of memory via caching and proper session management.<br>- Use of async endpoints where possible (FastAPI async support). | - API service (Uvicorn workers)<br>- Celery workers<br>- Database connection pool<br>- Redis cache | - Stress testing to observe CPU, memory, queue lengths.<br>- Monitor system metrics (CPU, memory, disk I/O, network).<br>- Verify that queue lengths remain low under high load. |
| NFR 1.3 | Queue Management: sudden spikes must not crash the system. | - Message broker (Redis/RabbitMQ) for Celery to buffer tasks.<br>- Rate limiting on API endpoints to prevent overload.<br>- Circuit breaker pattern for external dependencies (payment gateways).<br>- Auto-scaling policies (if deployed in cloud).<br>- Graceful degradation: if payment gateway is down, mark payments as failed and allow retry. | - Celery with Redis broker<br>- API rate limiting middleware<br>- Circuit breaker in payment service<br>- Monitoring and alerting | - Simulate traffic spikes and observe that requests are queued (not dropped) and processed eventually.<br>- Verify that system remains responsive (non-critical endpoints still work) during backend failures.<br>- Check that dead-letter queues are used for failed tasks. |
